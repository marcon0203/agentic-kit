## 一、摘要

AI Agent 平台让**每个用户**把基础能力（模型、Skill、插件、MCP、知识库）注册为自己的资源，组合成具备明确角色约束的 Agent，再把多个 Agent 动态编排成一个 **Bundle** 协作完成复杂任务；做得好的资源可以**发布到广场**供其他用户订阅使用，让平台从个人工具沉淀成社区资产。V1 聚焦信息架构里的**应用中心**和**资源中心**——尤其是已经通过技术原型验证过的核心机制：像"产品经理 → 架构师 → UI 设计师 → 全栈工程师"这样的角色 Agent，按 DSL 定义的协作图（并行分支、条件路由、human gate 人工审批）动态组合并执行，Web 端实时可视化整个协作过程。模型中心、运营中心、系统设置作为平台基础设施，V1 只做支撑核心场景运行的最小闭环，深化能力放到后续阶段。

## 二、背景与现状

**问题空间**：做 AI Agent 类产品的团队普遍要解决同一类问题——单个 Agent 能力有限，复杂任务需要多个专业角色协作，但业界现成框架（LangChain、CrewAI、Google ADK 等）解决的是"怎么跑一个 Agent"，没有解决"一个平台化产品要怎么让非技术团队成员也能配置、复用、审计这些协作流程"。

**已完成的验证**：本次对话过程中，我们从零验证了一版技术可行性：

- 设计了 Agent DSL（角色约束 + 能力白名单 + 协作契约）和 Bundle DSL（多 Agent 编排图，支持并行/汇聚/条件路由/human gate）
- 用 Go 实现了执行图引擎，SQLite 持久化，React 实时可视化前端
- 完整跑通浏览器端到端测试，过程中真实发现并修复了两个工程问题：自环重试边被错误计入 join 前置条件导致死锁；Go 的 nil slice 序列化成 JSON `null` 导致前端崩溃
- 围绕"要不要用现成框架"做了选型调研（Google ADK Go、Goa-AI、LangChainGo 等），结论倾向 ADK Go 2.0（详见配套架构文档）

**信息架构约束**：你提供的《AI Agent 平台信息架构 V4》给出了这套能力应该长在哪个产品结构里——应用中心（应用/智能体管理）、资源中心（Skill/插件/MCP/知识库）、模型中心（模型市场/Provider/路由）、运营中心（监控/日志/成本/审计）、系统设置（用户/团队/权限），核心模型是 `Application -> Agent -> Model/Skill/Plugin/MCP/KnowledgeBase`。这份 PRD 要做的事，就是把已验证的技术能力套进这套信息架构，变成一份可以排期开发的产品需求。

【假设】目标用户是企业内部的技术团队和产品团队，平台首期面向内部使用或小范围客户试点，不是要立刻支撑大规模对外 SaaS 多租户场景。如果实际定位不同，第三、四、七节的指标和权限设计需要相应调整。

## 三、目标与成功指标

**目标 Goals**：

1. 用户能在资源中心注册 Tool / Skill / MCP Server / 知识库，在应用中心把这些能力组合定义成具备角色约束的 Agent
2. 用户能把多个 Agent 按 DSL 编排成一个 Bundle（串行、并行、条件路由、human gate 审批节点），一键运行
3. 运行过程在 Web 端实时可视化：执行图、时间线、共享状态、审批交互全覆盖
4. 用户能把自己的 Agent / Bundle / Skill 等资源发布到广场，其他用户能浏览、订阅并直接使用，形成"创作—分享—复用"的正循环
5. 内部验证：用一个真实的 PM → 架构师 → UI 设计师 → 全栈工程师 Bundle，跑通一次"从需求到可运行代码"的协作闭环（对应已验证的 web-app-builder 示例）

**非目标 Non-Goals**：

1. 不做模型市场的第三方计费和结算体系——模型中心 V1 只做到"能接入、能路由、能统计 token"，商业化能力后置
2. **不做订阅审核流程**——发布即上架，靠举报下架和作者信誉机制兜底，审核体系后置
3. 不做付费订阅、分成、榜单排名等商业化与激励机制——V1 只解决"能不能分享和复用"
4. 不做资源的 fork / 二次创作——本期发布的资源是**黑盒**，订阅者只能调用不能查看和修改内部定义（见下方"广场与订阅的核心约束"）
5. 不做跨组织的公开互联网广场——V1 的广场边界是**同一平台实例内的全体用户**，不涉及跨实例分发
6. 不做移动端
7. 不做 Agent 执行效果的持续调优（prompt 工程、few-shot 优化）——这是运营期的持续工作，不是本期交付范围

**成功指标**：

| 指标 | 当前值 | 目标值 | 测量方式 |
|---|---|---|---|
| Bundle 创建到首次运行成功率 | 0（无该功能） | ≥ 80% | 运行日志统计，成功 = 跑到 END 或用户主动认可的终态 |
| 端到端协作平均耗时（4 角色 Bundle） | 无基线 | 内部试点后建立基线，目标 30 分钟内完成从需求到可运行代码 | 运营中心运行时长统计 |
| Human Gate 平均响应时长 | 无该功能 | < 10 分钟 | `human_gate.waiting` 到 `human_gate.resolved` 事件间隔 |
| 内部团队活跃 Bundle 数 | 0 | 上线 30 天内 ≥ 5 个团队沉淀出自己的 Bundle 模板 | 应用中心 Bundle 创建记录 |
| 因平台自身缺陷导致的运行失败率 | POC 阶段核心机制已验证可行 | 生产环境 < 1% | 运营中心错误日志分类统计 |

## 三点五、广场与订阅的核心约束

发布采用**黑盒**、订阅采用**快照隔离**，这两个决策组合起来对系统设计有几个不可回避的影响，先在这里说清楚，后面的用户故事和架构设计都建立在此之上：

**1. 黑盒意味着"能跑但看不见"，运行必须在作者的定义上执行**

订阅者拿到的不是一份定义的拷贝，而是一个**调用凭据**。运行时系统需要用作者的原始定义（persona、编排图、工具白名单）去执行，但任何接口、任何日志、任何报错都不能把这些内容泄露给订阅者。这条约束的具体后果：

| 场景 | 处理方式 |
|---|---|
| 订阅者查看已订阅的 Agent | 只返回展示信息（名称、角色、描述、作者、输入输出说明），`definition` 字段一律剥离 |
| 订阅者运行黑盒 Bundle | Chat 界面里 Agent 气泡正常显示产出内容，但右侧执行图只显示"黑盒节点"占位，不暴露内部编排结构 |
| 运行报错 | 错误信息需脱敏，不能把 persona 片段、内部节点名回传给订阅者 |
| 事件流 | `node.thinking` 这类会暴露内部推理过程的事件，对黑盒资源默认不推送给订阅者（只推 `node.started` / `node.finished`） |

**2. 快照隔离意味着"作者改版不影响已订阅的人"**

订阅关系必须绑定到**具体版本**，而不是资源的最新指针。作者发布 v1.1 后，已订阅 v1.0 的用户继续运行 v1.0，直到主动升级。这要求：

- 已被订阅的版本**不可删除、不可修改**，作者只能"停止分发"（不影响存量订阅者），或标记废弃（提示订阅者升级）
- 平台需要保留全部被订阅过的历史版本定义，存储成本随版本数增长
- 订阅者要能看到"有新版本可用"的提示，并且能看到作者填写的更新说明（更新说明是作者主动写的，不是 diff——因为 diff 会泄露黑盒内容）

**3. 成本与配额归属需要明确**

黑盒资源运行时消耗的 Token 算谁的？V1 的约定：**算订阅者的**，因为是订阅者发起的运行、消耗的是订阅者配置的模型 Provider。这带来一个衍生要求——黑盒 Agent 的 `constraints`（最大工具调用数、超时）必须对订阅者可见，否则订阅者无法预估自己会被消耗多少成本，这是黑盒规则的一个必要例外。

**【已决】依赖必须是完整的已发布闭包**——一个资源要发布，它**传递依赖的每一层**都必须已经发布，否则拒绝发布（错误码 70001）。

```
发布 Bundle
  └─ 它引用的每个 Agent          → 必须已发布
       └─ 每个 Agent 引用的 MCP  → 必须已发布
       └─ 每个 Agent 引用的 Skill → 必须已发布
       └─ 每个 Agent 引用的 Tool  → 必须已发布
```

这是**递归校验**，不只查直接引用那一层。任一层存在未发布的私有资源就整体拒绝，`details` 里给出完整的引用路径（如 `agents[1].capabilities.tools[2] → mcp/internal-search 未发布`），让作者知道该去发布哪个，而不是只说"有依赖没发布"。

**为什么必须这么严**：黑盒 + 快照隔离的组合下，订阅者运行的是作者的原始定义。如果某一层依赖是私有的，订阅者运行时必然失败，而黑盒规则又要求错误脱敏——订阅者会看到一个既无法理解也无法自行修复的失败。把问题挡在上架环节是唯一能给出清晰归因的时机。

不选"允许发布、运行时报错"：把作者的配置错误变成订阅者的运行失败。不选"作者代理调用"：涉及跨用户的凭证使用与配额归属，复杂度远超 V1。

**连带的约束**：已发布资源被其他已发布资源依赖时，**不能"停止分发"**（会让上游的依赖闭包断裂）。作者需先处理掉依赖它的上游资源，或接受它继续保持分发状态。这一条在 P0-10 的验收标准中体现。

## 四、目标用户与细分

平台的每个注册用户都拥有自己的资源空间，同一个人在不同场景下会切换下面几种身份：

| 用户角色 | 使用场景 | 主要落地页面（对应 IA） |
|---|---|---|
| **创作者** | 注册自己的 Skill / 工具 / MCP，定义 Agent，编排 Bundle；把满意的作品发布到广场，维护版本和更新说明 | 资源中心、应用中心、应用广场（我的发布） |
| **订阅者** | 在广场浏览别人的 Agent / Bundle，订阅后直接用，不关心内部实现 | 应用广场、我的订阅、Chat 运行页 |
| **使用者** | 不管资源是自建还是订阅来的，发起运行、在 Chat 里看协作过程、做 human gate 审批 | 首页快速创建、Chat 运行详情页 |
| 平台管理员 | 接入模型 Provider、管理用户、处理举报下架、看整体成本 | 模型中心、系统设置、运营中心 |
| 运维 / 合规角色 | 监控运行状态、追查失败原因、审计谁在什么时候批准了什么 | 运营中心 |

**当前的替代方案**：团队各自用 Claude Code / Cursor 之类的工具手动串起多轮对话，协作过程不可复用、不可审计、无法沉淀成团队资产；好的提示词和工作流只能靠截图、文档、口口相传在同事之间扩散——这是本平台"广场 + 订阅"要解决的第二层痛点。

## 五、用户故事与需求

### P0 — 必须做

| # | 用户故事 | 验收标准 |

| P0-7 | 作为 Bundle 使用者，我想查看某个 Agent 的完整产出以及运行的原始时间线，以便复盘和调试 | · 气泡上的"查看完整产出"可展开抽屉，显示该节点写入 shared_state 的结构化内容<br>· 右侧辅助栏的原始时间线按时间顺序展示全部事件（含 tool_call、thinking）<br>· 共享状态支持结构化 JSON 查看<br>· 运行结束后页面可直接刷新重看，历史事件完整回放 |
| P0-8 | 作为运维角色，我想在运营中心看到所有 Bundle 运行的列表和状态分布，以便发现异常 | · 列表支持按 Bundle / 状态 / 时间筛选<br>· 失败的运行能一键跳转到该次运行的完整时间线定位原因 |
| P0-9 | 作为新用户，我想注册账号并登录，拥有属于自己的资源空间 | · 支持邮箱注册 / 登录，JWT 会话<br>· 每个用户默认拥有一个私有空间，新建的资源默认仅自己可见<br>· 未登录只能访问登录/注册页 |
| P0-10 | 作为创作者，我想把我的 Agent / Bundle 发布到广场，以便其他人使用我的成果 | · 发布时选择资源、指定版本、填写展示名/描述/使用说明<br>· 发布前做**递归依赖闭包校验**：传递依赖的每一层（Bundle→Agent→MCP/Skill/Tool）都必须已发布，任一层未发布即拒绝<br>· 拒绝时 `details` 给出完整引用路径，并提供「去发布该依赖」的快捷入口<br>· 发布后生成广场条目<br>· **被其他已发布资源依赖的资源不可停止分发**，需先处理上游依赖 |
| P0-11 | 作为订阅者，我想在广场浏览和搜索别人发布的资源，并订阅我需要的 | · 广场支持按类型（Agent/Bundle/Skill/MCP）筛选、按名称搜索<br>· 详情页展示：展示名、描述、作者、使用说明、输入输出说明、执行约束（最大工具调用数/超时，用于预估成本）<br>· **不展示** persona、编排图、内部节点等黑盒内容<br>· 一键订阅，订阅关系绑定到发布时的**具体版本** |
| P0-12 | 作为订阅者，我想像使用自己的资源一样直接运行订阅来的 Bundle | · 已订阅资源出现在自己的资源列表中，带"订阅"标识和作者信息<br>· 运行流程与自建资源完全一致<br>· Chat 页中黑盒节点的产出正常展示，但执行图只显示占位节点，不暴露内部结构<br>· 运行消耗的 Token 计入订阅者账户 |
| P0-13 | 作为创作者，我想发布资源的新版本，同时不影响已经在用旧版本的订阅者 | · 发布新版本后，存量订阅者继续运行原版本（快照隔离）<br>· 已被订阅的版本不可删除、不可修改<br>· 订阅者在资源列表中看到"有新版本"提示和作者填写的更新说明，可手动升级<br>· 升级为显式操作，不自动生效 |

### 3. 运行详情页 — Chat 对话式（对应 P0-4 ~ P0-7）

运行详情页采用 **Chat 对话框**形态：用户在输入框里描述需求发起运行，多个 Agent 的产出以"不同角色发言"的形式流式出现在对话流里，human gate 审批作为一张内联卡片插在对话中间。右侧栏放执行图和共享状态作为辅助视图。

## 七、方案概述

技术方向延续本次对话已验证的原型（`agent-bundle-kit`）和后续选型调研，完整架构见配套的《架构设计文档》，这里只点几个关键决策：

- **Bundle 编排引擎**：调研过手写引擎 vs Goa-AI vs Google ADK Go 2.0 三个方向，结论倾向 **ADK Go 2.0**——其 2026 年 6 月发布的图执行引擎、内置 human-in-the-loop、进程重启状态恢复，覆盖了原型阶段手写实现暴露出的大部分问题
- **DSL 设计**：沿用已验证的 Agent DSL + Bundle DSL（JSON Schema 校验），P0-2/P0-3 的表单直接映射这套 DSL 字段
- **事件流**：沿用已验证的 chunked HTTP NDJSON 方案（不是 WebSocket 也不是 SSE），单一长连接、300ms 内部检查间隔，实测端到端只产生 1 个 HTTP 请求
- **数据存储**：POC 阶段 SQLite，生产环境多实例部署时升级为 Postgres

## 八、已决事项（原待确认项的结论）

以下问题在文档编写过程中逐一决断，**V1 范围内不留悬空待办**。若后续要推翻，需同步修改架构文档对应章节。

| 原问题 | 结论 | 依据 / 影响 |
|---|---|---|
| ADK Go 2.0 是否采用、迁移成本多大 | **采用**。迁移工作作为正式任务 `task#10` 排期，不是可选调研 | ADK 2.0 的图执行 + 内置 HITL + 崩溃恢复恰好覆盖 POC 手写实现的短板；风险缓解见架构文档（调用收敛单包 + 锁定次版本 + 保留 `AgentRunner` 抽象边界） |
| 模型成本分摊口径 | **算发起运行的人**。黑盒资源运行消耗的 Token 计入订阅者账户，因为是订阅者发起、用的是订阅者自己配置的 Provider 凭证 | 衍生要求：黑盒资源必须公开执行约束（工具调用数/超时/预计 Token），否则订阅者无法预估成本——这是黑盒规则的必要例外 |
| human gate 审批人权限模型 | **角色级，不到人**。`human_gates[].approver_roles` 配置角色；未配置时默认为运行发起人本人 | 已提升为 P0-19。到人的粒度会让 Bundle 定义与具体用户绑定，无法作为可分享的资源发布 |
| V1 是否做多租户数据隔离 | **不做**。V1 按"单平台实例内的多用户"模型，资源归属到 `owner_user_id`，权限规则是"自己的 + 订阅的" | 已写入非目标第 5 条。广场的边界是同一平台实例内的全体用户，不涉及跨实例分发 |
| 认证是独立页面还是弹窗 | **弹窗**。全局身份组件，以 modal 形式存在于 app shell 内 | 设计系统硬性规定，见 `design-system.md`。已修正 spec-13 |
| 整体视觉是深色还是浅色 | **浅色**。页面 `#f6f7fb`、卡片 `#ffffff` | tokens-pc.md 是唯一权威来源；V1 不做深色模式 |

## 延伸建议

- **要不要先做 P0 范围的 pre-mortem？** 多 Agent 协作类产品最容易低估的风险通常在"human gate 卡住没人处理"和"DSL 校验规则和真实执行行为不一致"这两类——这两个我们在原型阶段都真实踩过。
- **要不要把 P0 的 8 条故事再拆一层？** 现在这个粒度大概率还需要拆成更小的开发任务才能排期，可以用 `user-stories.md` 的方法论继续往下拆。
- **要不要现在启动 ADK Go 2.0 的迁移 spike？** 这个决策会直接影响架构文档里编排引擎那一整章的写法，越早验证越好。
