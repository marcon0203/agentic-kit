# 事件流（NDJSON）多实例部署说明

> 对应 `spec/spec-12-event-stream.md` 的「多实例部署」章节。

## 问题

`GET /runs/{id}/stream` 是一个长连接的 chunked HTTP 响应，执行run的引擎
goroutine常驻在某一个 server 实例的内存里（`RunEngine.cancels` /
`gateRegistry` 均是进程内状态）。一旦部署多个 server 实例，负载均衡器可能把
同一个 run 的 stream 请求路由到没有运行该 run 的实例——这个实例照样能查询
Postgres 里的 `bundle_run_events`，把已经落库的事件转发出去，所以**不会
出错，但可能出现"引擎实例继续产生新事件时，另一个实例没有更快的方式感知，
只能靠现有的轮询"**。V1 用会话粘性（同一个 run_id 固定路由到同一实例）把
这个问题降到最低。

## 方案：Nginx 会话粘性（按 run_id 路由）

按 URL 里的 `run_id` 做一致性哈希，而不是按客户端 IP／cookie——同一用户的
不同 run 完全可以分散到不同实例，只有同一个 run 的多次请求（stream 建连、
断线重连、cancel、gate 审批）需要落到同一实例。

```nginx
# nginx.conf（片段）——反向代理 /api/v1/runs/* 到后端实例组
upstream agentic_kit_backend {
    # 一致性哈希：从 URI 中提取 run_id 作为 key，
    # 同一个 run_id 的所有请求稳定落到同一台后端。
    hash $run_id consistent;
    server backend1:8080;
    server backend2:8080;
    server backend3:8080;
}

server {
    listen 80;

    # 从 /api/v1/runs/{id}/... 中截取 run_id，供上面的 hash 使用。
    location ~ ^/api/v1/runs/(?<run_id>[^/]+) {
        proxy_pass http://agentic_kit_backend;
        proxy_http_version 1.1;

        # 关键：不设置的话 nginx 会攒够一个 buffer 才转发，
        # chunked NDJSON 流式响应会退化成"伪流式"（一次性吐完）。
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;   # stream 连接可能长时间挂起等待事件

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    location /api/v1/ {
        proxy_pass http://agentic_kit_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

验证代理确实是真流式（而非攒完一次性转发）：

```bash
curl -N http://<nginx>/api/v1/runs/<run_id>/stream \
  -H "Authorization: Bearer $TOKEN"
# 应观察到事件随执行进度陆续打印，而不是等待若干秒后一次性输出。
```

## 实例故障时的行为

一致性哈希在某个后端实例下线时，只会重新分布落在**那台实例**上的 key，
不会像取模哈希那样让全部 run 重新洗牌。客户端 stream 连接断开后按
`after_id`（已收到的最后一个事件 id）重连即可续传，不会丢失也不会重复
——这是 event 持久化到 `bundle_run_events` 之后才转发的直接结果：只要
Postgres 里有记录，任何实例都能从 `after_id` 之后继续补发。

真正受影响的是**该实例内存中未完成的运行**（`RunEngine.cancels` 里的
`context.CancelFunc`、`gateRegistry` 里等待中的 gate）——这部分状态会随
实例重启丢失，这是 V1 明确的已知限制（架构设计文档："POC 阶段的
ChannelGateProvider（内存 channel）明确标注过服务重启会丢失所有待处理的
gate"），需要人工介入或等实例数上来后评估用 PostgreSQL LISTEN/NOTIFY 或
其他共享事件总线替代进程内 channel。

## 何时需要升级到共享事件总线

会话粘性只在实例数较少、run 的执行时长不太长时够用。当以下任一条件出现时
应评估引入 PostgreSQL LISTEN/NOTIFY（或 Redis pub/sub）把 `RunEngine` 的
事件广播和 gate 解锁做成跨实例共享，而不是依赖单实例内存：

- 实例数增长到负载均衡的一致性哈希开始出现明显倾斜；
- 运行时长经常超过单个实例的正常运维周期（滚动发布会打断内存态）；
- 需要"任意实例都能审批任意 run 的 gate"这种去掉粘性约束的能力。
