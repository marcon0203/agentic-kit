# 插件开发指南

本文档面向两类读者：

- **第三方插件开发者**：想给 agentic-kit 写一个插件（数据库连接器、图表渲染器、自定义工具……），通过组件广场的"插件"市场分发。
- **平台内置插件开发者**：要在 agentic-kit 代码库里新增一个随服务端二进制一起发布的内置插件（`internal/builtinplugins`）。

两者共享同一份 `plugin.json` 清单规范和同一套运行时能力，区别只在"怎么把插件交给系统"这一步——第三方插件走签名上传+审核，内置插件走编译期嵌入。本文档先讲两者共用的基础，再分别讲两条落地路径。

---

## 1. 核心概念

- **插件（Plugin）**：一个 `.akp`（zip 格式）包，根目录下必须有 `plugin.json` 清单，可选带一个 WASM 模块（`plugin.wasm`）、静态前端资源（`ui/`）、其它资源（`assets/`）。
- **manifest_version**：清单规范版本，当前恒为 `1`。
- **扩展点（extensions）**：一个插件可以同时声明多种能力：
  - `tools[]` — 模型可调用的工具（跑在 WASM 里）
  - `renderers[]` — 前端渲染器（纯静态 HTML/JS，跑在 iframe 里，不需要 WASM）
  - `connectors[]` — 数据库连接器的方言/schema 映射（跑在 WASM 里，但真正的连接由宿主管理）
  - `hooks[]` — 在工具调用/模型响应前后插入逻辑（跑在 WASM 里）
- **统一命名空间**：一个插件安装后，它的 `tools[]` 和 `renderers[]` 都会被解析成 `plugin:{plugin_id}/{name}` 这样的 ref，和资源中心的组件 ref 写进同一个 Agent DSL `capabilities.tools[]` 数组——Agent 作者不需要关心一个 ref 到底来自资源中心还是插件。
- **运行时**：WASM 模块用 [Extism](https://extism.org/) 加载执行，插件代码可以用任何能编译到 `wasm32-wasip1`（或 Extism 支持的其它 wasm target）的语言写，官方样例用 Rust + `extism-pdk`。

## 2. `plugin.json` 清单规范

Schema 定义在仓库的 [`schemas/plugin.schema.json`](../schemas/plugin.schema.json)，两类插件都必须通过它的 JSON Schema 校验。核心字段：

```jsonc
{
  "manifest_version": 1,
  "id": "acme.charts",            // 全局唯一，反向域名式，发布后不可改
  "version": "1.0.0",             // 语义化版本号
  "display_name": "图表渲染器",
  "description": "……",           // 最长 500 字符
  "author": { "name": "Acme", "url": "https://acme.example" },
  "license": "MIT",
  "icon": "icon.png",             // 包内相对路径，可选

  "requires": {
    "host_api": ">=1.0 <2.0",     // 宿主 API 版本区间
    "services": ["sql"],          // 需要用到的 host 服务：sql / kv / log / http
    "network": ["api.example.com"],       // 出网白名单，其余一律拒绝
    "permissions": ["read:run_output"]    // 细粒度权限，安装时展示给用户
  },

  "extensions": {
    "tools": [ /* 见 2.1 */ ],
    "renderers": [ /* 见 2.2 */ ],
    "connectors": [ /* 见 2.3 */ ],
    "hooks": [ /* 见 2.4 */ ]
  }
}
```

`extensions` 允许出现未知字段（`additionalProperties: true`）——这是给未来新扩展点留的口子，宿主解析到不认识的类型会直接跳过，不会因此拒绝整份清单。

### 2.1 `tools[]` — 模型可调用的工具

```jsonc
{
  "name": "run_query",                    // ^[a-z][a-z0-9_]*$
  "description": "在已绑定连接上执行只读 SQL 查询",
  "input_schema": {                       // 标准 JSON Schema，描述模型该传什么参数
    "type": "object",
    "required": ["query"],
    "properties": { "query": { "type": "string" } }
  },
  "entry": "plugin.wasm#run_query",       // "<包内文件>#<wasm 导出函数名>"
  "ui": "ui/result-card.html"             // 可选：返回结果需要自定义 UI 时的入口
}
```

调用一个 `tools[]` 工具时，宿主把模型传入的参数序列化成 JSON，写进 WASM 内存，调用 `entry` 里声明的导出函数，函数返回的 JSON 就是工具结果——具体的内存搬运细节由 Extism PDK 处理，插件代码只需要用 PDK 提供的宏声明一个普通函数。

`ui` 字段是 §4.2 方法 A："模型显式调用这个工具，调用成功后把结果渲染成卡片"——内置图表渲染器（`internal/builtinplugins/chartrenderer`）就是这么做的：`render_chart` 工具的 `input_schema` 描述 `{type, title?, labels, datasets}` 这个形状，模型调用时参数已经按 schema 校验过，wasm 侧的 `render_chart` 导出函数不做任何真正的计算，只是校验+原样返回，让这次调用是一次真正的、在事件流里有确定先后顺序的工具调用；结果直接交给 `ui: "ui/chart.html"` 渲染。

**优先用这种方式**，而不是下面 2.2 节的 `auto_render`：工具调用是模型的一个显式动作，在时间线上有准确的位置——如果 Agent 先说一段话、再展示图表、后面还要接着说别的，图表卡片会准确地出现在它被调用的那个时间点；`auto_render` 做不到这一点，见下文。

### 2.2 `renderers[]` — 前端渲染器（`auto_render`，谨慎使用）

```jsonc
{
  "name": "chart",
  "entry": "ui/chart.html",               // 包内相对路径，纯静态 HTML/JS
  "description": "要渲染图表，回复中放一个 ```chart 代码块，内容是这样形状的 JSON：{\"type\": \"bar\"|\"line\"|\"pie\", \"labels\": [...], \"datasets\": [{\"label\": \"...\", \"data\": [...]}]}",
  "auto_render": {
    "fenced_lang": ["chart"]              // 模型回复里出现 ```chart 代码块时自动接管渲染
  }
}
```

渲染器**不需要 WASM**，也不需要模型显式调用——`auto_render.fenced_lang` 命中即接管。运行时通过一个独立、不带鉴权的资源域（`GET /plugins/assets/{id}/{ver}/{path}`）把 `entry` 指向的 HTML 连同它引用的其它文件下发给 iframe，和普通静态资源 CDN 的访问方式一样。

> **顺序问题，先想清楚再用**：`auto_render` 是"整条消息说完之后，对完整文本做正则匹配"——渲染事件永远排在这个节点全部文字之后，不管那段 fenced 代码块在模型输出里实际处于开头、中间还是结尾。如果模型的输出是"图表如下：〈代码块〉，以上数据说明……"这种前后都有文字的结构，图表卡片仍然只会出现在消息末尾，和后面那段说明文字的相对顺序是错的。内置图表渲染器早期就是这么做的，已经改成 2.1 节的工具调用方式；`auto_render` 现在只建议用在"渲染内容就是整条回复、前后不会再有别的文字"这种场景。
>
> **重要**：一个 `auto_render` 注册要真正生效，它的 `plugin:{id}/{name}` ref 仍然必须出现在某个 Agent 的 `capabilities.tools[]` 里——装了插件不等于渲染器自动生效，Agent 编辑器的能力选择器里勾选一下这个 ref 才行（`GET /plugins/installed/tools` 返回的列表里能找到它）。
>
> **`description` 强烈建议填**：和 `tools[]` 不同，`auto_render` 命中不经过模型的 function-calling 接口，宿主没有别的渠道告诉模型该往 fenced code block 里写什么——不写 `description`，模型只能瞎猜 JSON 形状。运行时会把这里写的内容原样拼进 Agent 的系统提示词，所以直接写清楚字段形状 + 一个示例就够了，不需要额外的 schema 格式。

### 2.3 `connectors[]` — 数据库连接器

```jsonc
{
  "name": "postgres",
  "kind": "sql",                          // 目前只有 "sql"
  "entry": "plugin.wasm#dialect_hook",     // 只做方言/schema 映射，不是必需的
  "config_schema": { /* 建连接时要用户填什么，allow_write 由宿主统一注入 */ }
}
```

绝大多数 SQL 连接器插件不需要单独声明 `connectors[]`——真正常见的做法是在 `tools[]` 里声明 `list_tables`/`run_query`/`run_write` 这类工具，调用宿主注入的 `sql.query`/`sql.execute`/`sql.schema` host function（见第 4 节）。`connectors[]` 这个扩展点是给需要自定义方言映射的场景预留的，内置的 Postgres/MySQL 连接器都没有用到它——同一份 WASM 模块靠连接自身携带的 `dialect` 字段区分方言，插件代码完全不用关心。

真正把一个连接器插件和一个真实数据库绑定起来，靠的是清单里自定义的 `connector_hint` 扩展（见 2.5）+ 安装时的 `connector_resource_id` 配置（见第 6 节）。

### 2.4 `hooks[]` — 调用链路钩子

```jsonc
{
  "point": "before_tool_call",    // before_tool_call / after_tool_call / before_response / after_response / on_error
  "entry": "plugin.wasm#on_before_tool_call"
}
```

对应 Agent DSL `capabilities.hooks{}` 的同名字段。一个插件在一个 `point` 上最多声明一条（不像 `tools[]`/`renderers[]` 有 `name`，`hooks[]` 靠 `point` 唯一标识）。每次调用有硬性 **5 秒超时**，超时或出错会优雅降级（跳过这次 hook，不影响主流程），不会拖垮整条调用链路。要修改响应内容（比如 `after_response` 改写模型输出），必须在 `requires.permissions` 里声明对应的 `write:*` 权限，宿主按声明校验，没声明的一律没有。

### 2.5 自定义扩展：`connector_hint`

`extensions` 允许附加自定义字段，内置的两个数据库连接器插件用这个约定告诉前端"这是一个连接器插件，安装时需要额外收集连接信息"：

```jsonc
"extensions": {
  "tools": [ /* list_tables / run_query / run_write */ ],
  "connector_hint": {
    "dialect": "postgres",     // 或 "mysql"
    "default_port": 5432
  }
}
```

前端（组件广场的插件安装弹窗）检测到 `connector_hint` 存在，就会多渲染一个连接配置表单（host/port/database/username/password/是否允许写），安装时先把这些信息存成一个 `component_type=connector` 的组件资源（密码等敏感字段自动加密），再把这个资源的 id 作为 `connector_resource_id` 写进插件的安装配置——这一整套约定不是 `plugin.schema.json` 强制的协议，是内置连接器插件和前端之间的一个"民间约定"，你的第三方插件如果也需要绑数据库连接，照着抄同样的字段名即可。

## 3. 第三方插件开发流程

### 3.1 环境准备

参考仓库自带的完整可编译样例：[`examples/plugins/sql-connector`](../examples/plugins/sql-connector)（Rust + [`extism-pdk`](https://crates.io/crates/extism-pdk)）。

```sh
rustup target add wasm32-wasip1   # 一次性
cargo build --release --target wasm32-wasip1
# 产物：target/wasm32-wasip1/release/<crate_name>.wasm
```

不必用 Rust——任何能编译到 wasm32 且有 Extism PDK 绑定的语言都可以（Go、AssemblyScript、C 等，见 [Extism 官方 PDK 列表](https://extism.org/docs/concepts/pdk)）。

### 3.2 声明并调用 host functions

宿主给每个编译好的插件注入一组固定的 host function（宿主实现在 `internal/adapter/extism/host_functions.go`），插件侧用 PDK 的 `#[host_fn]`（Rust）或等价机制声明后即可调用：

| host function | 作用 | 请求字段 | 响应字段 |
|---|---|---|---|
| `sql_query` | 只读查询 | `conn_ref, sql, args` | `rows: [{...}]` |
| `sql_execute` | 写语句（是否真的允许写由连接的 `allow_write` 绑定决定，不由插件判断） | `conn_ref, sql, args` | `affected_rows` |
| `sql_schema` | 列出表名 | `conn_ref` | `tables: [string]` |
| `kv_get` | 读一个插件私有 kv 值（按 `插件id:owner_id` 自动隔离命名空间） | `key` | `value, found` |
| `kv_set` | 写一个插件私有 kv 值 | `key, value` | — |

每个调用返回的信封统一是 `{"ok": bool, "error"?: string, ...其它字段直接展开}`——`ok=false` 时插件必须自己检查并处理，Extism 调用本身只在传输/内存层面失败时才报错，宿主逻辑（比如 `allow_write` 拒绝）永远走 `ok=false` 这条路，不是异常。

`sql.*` 系列用到的 `conn_ref` 从哪来？插件永远拿不到数据库连接串或密码，只能通过 `config::get("connection_ref")`（Extism 的插件配置读取接口）拿到一个不透明的引用——这个值由宿主在授权阶段注入，细节见第 6 节。

日志用 Extism SDK 自带的 log/var 机制即可（PDK 通常暴露 `extism_pdk::log` 之类的接口），不是一个单独的 host function。

### 3.3 编写 plugin.json 并打包成 .akp

`.akp` 就是一个 zip，根目录下固定布局：

```
plugin.json          # 必须
plugin.wasm          # tools[]/connectors[]/hooks[] 任一非空时必须
ui/                  # renderers[]/tools[].ui 引用的静态文件
assets/              # 其它静态资源
README.md            # 可选
```

打包时把这些文件放进一个 zip 即可，没有额外的 CLI 工具要求。

### 3.4 生成签名密钥对并注册公钥

发布者本地生成一对 Ed25519 密钥（私钥永远不上传，只在本地保存），把公钥注册到平台：

```http
POST /plugins/signing-key
Content-Type: application/json

{ "public_key": "<32 字节公钥的 base64>" }
```

再次调用会**轮换**（覆盖）已注册的公钥。

### 3.5 计算签名并上传

签名对象是 **`.akp` 包原始字节的 SHA-256 摘要**，用第 3.4 步的私钥对这个摘要做 Ed25519 签名：

```
digest    = SHA256(akp 包的原始字节)
signature = Ed25519_Sign(私钥, digest)
```

```http
POST /plugins
Content-Type: multipart/form-data

signature=<base64 编码的签名>
zip=<.akp 包二进制>
```

`plugin_id`/`version` 不需要单独传，服务端从包内 `plugin.json` 里读。校验链路依次是：manifest 过 JSON Schema → 验签（未注册签名公钥 400/100006，验签失败 400/100003）→ 体积上限 50 MiB（超出 400/100004）→ **自动化门槛**：`tools[]`/`connectors[]`/`hooks[]` 每一条声明的 `entry` 导出函数名，都会真的去编译后的 wasm 模块里验证存在（不存在 400/100004）——manifest 声称有的能力，实际编译产物里必须真的有，这一步在上传时就拦下来，不会等到 Agent 第一次调用才发现。

全部通过后，这个版本以 `visibility=private`、`review_status=pending` 落库——**发布者立刻可以自己安装试用**，公开上架是另一个独立的动作（见 3.7）。

### 3.6 私有安装自测

```http
POST /plugins/{plugin_id}/install
Content-Type: application/json

{ "version": "1.0.0" }   // 不传则装最新版本
```

未公开上架的版本，只有发布者本人能装。装完之后就能在组件广场的插件市场看到"已安装"标记，去 `/agents/new` 编辑器的"技能"分段勾选这个插件的工具/渲染器 ref 即可测试。

### 3.7 申请上架

```http
PATCH /plugins/{version_id}          # 注意这里的 {id} 是版本的数字行 id，不是 plugin_id
Content-Type: application/json

{ "visibility": "public" }
```

切到 `public` 会进入管理员审核队列（`GET /moderation/plugins`），**不是**立即可安装——要等管理员在运营中心通过审核（`POST /moderation/plugins/{version_id}/review`，`{"approve": true}`）之后，`review_status` 才变成 `passed`，这时才会出现在 `GET /plugins/market`（组件广场公开列表）给所有用户看到。切回 `private` 会退出审核队列。

### 3.8 常见校验失败点

- **`manifest id/version` 和上传参数不一致**：`plugin.json` 里的 `id`/`version` 必须和实际打包的一致（服务端会双重校验）。
- **声明了 `entry` 但没有对应的 `plugin.wasm`**：`tools[]`/`connectors[]`/`hooks[]` 任一非空，包里就必须有 `plugin.wasm`。
- **导出函数名对不上**：`entry: "plugin.wasm#run_query"` 里 `#` 后面的函数名，必须和 wasm 编译产物里真实导出的函数名完全一致（大小写敏感）。
- **忘记注册签名公钥**：第一次上传前必须先调用 `POST /plugins/signing-key`。
- **签名对象搞错**：签的是**包字节的 SHA-256 摘要**，不是包字节本身，也不是 manifest 的摘要。

## 4. 内置插件开发流程

内置插件是随服务端二进制一起发布的插件——它的"供应链"就是"在这个仓库的源码树里"，不需要签名、不需要审核，`publisher_id` 为 `NULL`（对应 spec-20 的"平台内置"约定），安装到用户账号后立刻可用。

### 4.1 目录结构

```
internal/builtinplugins/
├── builtinplugins.go          # go:embed 声明 + SeedAll
├── builtinplugins_test.go
├── wasm_integration_test.go   # 用真实 Extism 运行时校验嵌入的 wasm 能解析导出函数
├── postgresconnector/
│   ├── plugin.json
│   └── plugin.wasm
├── mysqlconnector/
│   ├── plugin.json
│   └── plugin.wasm            # 和 postgres 那份是同一个编译产物——方言在连接资源上，不在插件上
└── chartrenderer/
    ├── plugin.json
    └── ui/chart.html          # 纯前端渲染器，没有 wasm
```

`SeedAll(ctx, pluginService)` 在服务端每次启动时都会调用一遍（`cmd/server/main.go`），对每个内置插件调用 `plugin.Service.SeedBuiltin`——按 `plugin_id + version` 幂等，已经存在的版本直接跳过，不是错误。

### 4.2 新增一个内置插件

1. 在 `internal/builtinplugins/` 下新建一个子目录（比如 `myplugin/`），放 `plugin.json` + 需要的 `plugin.wasm`/`ui/*` 文件——清单规范和第 2 节完全一样。
2. 在 `builtinplugins.go` 里加一条 `//go:embed myplugin/plugin.json myplugin/plugin.wasm`（renderers-only 的插件就只 embed `plugin.json` 和它的 `ui/*` 文件，不需要 wasm）。
3. 在 `SeedAll` 的 `builtins`/`manifestPaths` 两个切片里追加一项，`files` map 按"OSS 相对路径 → embed.FS 内路径"填。
4. 重新编译、重启服务——下次启动 `SeedAll` 跑过之后，这个插件就出现在 `GET /plugins/market`，任何用户都能直接安装。

### 4.3 版本更新的坑

`SeedBuiltin` 是按 `plugin_id + version` 幂等的——**只改 `plugin.json` 内容但不改 `version` 号，在一个已经跑过一次种子的部署环境里不会生效**（因为这个版本号在库里已经存在，`SeedBuiltin` 直接返回已有记录，不会重新校验/重新写入）。改内置插件的 manifest（比如加一个新的 `tools[]` 条目）必须同时把 `version` 往上提一格，或者是全新的部署环境（数据库是空的）。

### 4.4 内置插件 vs 第三方插件对照

| | 第三方插件 | 内置插件 |
|---|---|---|
| 交付方式 | 上传 `.akp`（`POST /plugins`） | 编译进服务端二进制（`go:embed`） |
| 签名 | 必须（Ed25519） | 不需要 |
| `publisher_id` | 上传者的用户 id | `NULL`（平台内置） |
| 初始可见性 | `private` + `review_status=pending` | 立即 `public` + `review_status=passed` |
| 上架流程 | 发布者切 `visibility=public` → 管理员审核 | 无——种子即上架 |
| 谁能立刻安装 | 只有发布者自己（审核通过前） | 所有用户 |
| 更新一个已发布版本 | 不行——发新版本号 | 同样必须提版本号，否则种子直接跳过 |
| 校验链路 | manifest schema + 验签 + 体积上限 + wasm 自动化门槛 | manifest schema + wasm 自动化门槛（跳过验签） |

---

## 5. 一个插件的能力如何被 Agent 引用

1. 用户在组件广场"插件"Tab 安装插件（或已经是内置插件、默认可安装）。
2. `GET /plugins/installed/tools` 把这次安装的 `tools[]` 和 `renderers[]` 都解析成 `plugin:{plugin_id}/{name}` 形式的 ref，Agent 编辑器（`/agents/new`）"技能"分段的能力选择器里能看到。
3. 把这个 ref 勾进 Agent 的 `capabilities.tools[]`（和资源中心的组件 ref 是同一个数组，写法完全一样）。
4. 运行时：
   - `tools[]` 来源的 ref → 模型可以像调用普通工具一样调用它。
   - `renderers[]` 来源的 ref（`auto_render`）→ 只有出现在这个数组里，对应的自动渲染才会真正生效；没有被任何 Agent 引用的渲染器安装了也不会工作。

---

## 6. 连接器插件如何绑定真实数据库

以内置的 PostgreSQL/MySQL 连接器为例，完整链路：

1. 插件清单声明 `connector_hint`（见 2.5），前端据此在安装弹窗里多渲染连接配置表单。
2. 安装时，前端先调用 `POST /resources` 创建一个 `component_type=connector` 的组件资源（`{dialect, host, port, database, username, password, allow_write}`，密码等字段按现有约定自动加密存储）。
3. 再调用 `POST /plugins/{id}/install`，把上一步资源的 id 作为 `config.connector_resource_id` 传进去。
4. 运行时，`resourceAuthorizer.bindConnector`（`internal/adapter/orchestrator/plugin_authorizer.go`）在授权阶段：解出 `connector_resource_id` → 取出对应资源、解密其配置 → 向连接池申请一个真实连接 → 把一个不透明的 `connection_ref` 通过插件配置注入给 WASM 侧。
5. 插件代码全程只看得到 `connection_ref`，通过它调用 `sql.query`/`sql.execute`/`sql.schema`（第 3.2 节）——拿不到、也不需要知道真实的 DSN、账号、密码。
6. 写操作是否真的被允许，由连接资源自身的 `allow_write` 决定，宿主在 `sql_execute` 里强制校验——插件无论怎么构造请求都绕不过这一步。

## 7. 安全模型速览

- **网络白名单**：`requires.network[]` 声明的域名之外，WASM 沙箱内一律不能出网。
- **权限声明**：`requires.permissions[]`（`read:*`/`write:*`）是用户安装时能看到的授权项，尤其是 `hooks[]` 改写响应内容必须声明对应的 `write:*`。
- **wasm 自动化门槛**：上传/内置种子时都会校验 manifest 声明的每个 `entry` 在编译产物里真实存在。
- **hook 超时**：每次 hook 调用硬性 5 秒超时，超时或异常自动降级为跳过，不阻塞主流程。
- **凭证隔离**：连接器插件永远拿不到数据库真实凭证，kv 存储按 `插件 id : owner_id` 自动隔离命名空间，一个插件读不到另一个插件、或另一个用户的 kv 数据。
