# 模型渠道插件体系设计（Model Channel Descriptor, MCD）

> 状态：设计稿，待评审后分阶段实现
>
> 目标：新增一个模型厂商 = 提交一份 JSON，不改 Go、不发版本。**流式是一等公民，不是补丁。**

---

## 一、系统概览

### 【系统定位】

把"agentic-kit 怎么调一家模型厂商"这件事，从 Go 代码里搬到一份可安装、可版本化、可审核的声明式描述符里；宿主只保留凭据、出网、重试、计费、降级这些**不能交给插件**的职责。

### 【核心挑战】

1. **流式必须声明式表达。** 现有 `anthropic.CompleteStream` 是 130 行手写状态累加（`content_block_start` 开槽、`input_json_delta` 攒 JSON、`content_block_stop` 才能解析）。这类逻辑用"响应路径映射"根本表达不了——业界同类方案（如影策 open-ai-canvas 的 `yingce.plugin/v2`）在这里直接放弃了流式，把流归一成最终响应。我们不能。

2. **声明式的通病是错了不知道。** 手写 client 编译期就能挡住的错误，描述符里要到运行时才炸，而且报错是"路径取不到值"这种没法定位的形式。这套体系如果没有配套的加载期校验 + 自带回归用例，加渠道的成本只是从"写 Go"变成"调 JSON 调一天"。

3. **流式 + 降级链有语义冲突。** `Gateway.CompleteStream` 现在走 `resolve` 的 fallback 链。一旦第一环已经吐了半段文字才失败，切到第二环重新生成，前端会出现两段拼接的内容。这个 bug 现在就存在，做描述符时必须一并定掉。

### 【设计原则】

- **描述符只做协议翻译。** 它产出一个 `RequestSpec`（方法/路径/头/体），由宿主发包；它消费响应字节，产出统一结果。它不持有凭据、不发 HTTP、不重试、不计费。
- **能力有限优于表达力强。** 表达式算子、状态机操作都是封闭小集合，可枚举、可校验、可 fuzz，绝不图灵完备。宁可某个偏门渠道退回手写 Go client，也不给描述符加一个"万能"算子。
- **混合而非纯洁。** 手写 client 和描述符 client 在同一个 `ProviderDefinition` 注册表里平权共存。Anthropic 这种协议怪的，描述符写得难看就继续手写。

### 【假设与约束】

- 【假设】首期只覆盖**文本对话 + 工具调用 + 向量化**三类能力。图片/视频那种"提交任务→轮询→下载"的异步渠道留到 P4，但描述符结构预留 `task` 段不至于以后推翻重来。
- 【假设】多模态输入（图片入参）暂不在首期范围。`messages` 段的 `parts` 结构为它留了位置。
- 【约束】不改动 `Gateway`、`internal/orchestrator/adk/model_adapter.go` 和编排层的任何接口。描述符体系必须能整个塞进 `ProviderDefinition` 背后。
- 【约束】凭据继续走现有的 `provider_keys` 加密存储和 `ProviderKeyStore`，描述符只能声明"我需要哪几个字段"。

第 ② 条是白捡的：`schemas/plugin.schema.json` 的注释里已经预留了这个口子（"extensions 下未知的扩展点类型直接忽略……留给以后加扩展点（如 providers）"）。挂上去之后，模型渠道立刻拥有安装 / 版本 / 可见性 / 审核 / 市场分发的完整生命周期——这些都已经建好了。

| 层 | 职责 | 谁拥有 |
| --- | --- | --- |
| 描述符 | 请求模板、消息形状、响应路径、流式状态机 | 插件作者 |

| 出网 | HTTP client、超时、TLS、代理 | 宿主 |
| 编排 | 降级链、计费、事件流 | 宿主（Gateway） |

## 三、描述符规范

### 3.1 顶层结构

```jsonc
{
  "descriptor_version": 1,
  "id": "openai-chat",
  "label": "OpenAI Chat Completions",
  "wire": "openai.chat.v1",              // 线协议族标识，同族可共享 fixtures
  "capabilities": ["text", "tools", "stream", "embed"],
  "base_url": "https://api.openai.com",

  "credentials": [                       // 驱动前端表单 + provider_keys 存储
    { "name": "api_key", "type": "secret", "label": "API Key", "required": true },
    { "name": "base_url", "type": "url",   "label": "接口地址", "required": false }
  ],
  "auth": { "driver": "bearer", "credential": "api_key" },

  "limits": { "timeout_ms": 120000, "connect_timeout_ms": 10000 },

  "messages":  { /* 3.3 */ },
  "complete":  { /* 3.4 */ },
  "stream":    { /* 3.5 ★ */ },
  "embed":     { /* 可选 */ },
  "probe":     { /* 连通性校验，对应现有 Validator */ },
  "fixtures":  ["fixtures/basic.json", "fixtures/tools.json"]
}
```

`capabilities` 是**声明**，加载期会和实际存在的段交叉校验：声明了 `stream` 却没有 `stream` 段 → 加载失败。这比运行时才发现"这个渠道其实不支持流"要好得多。

### 3.2 表达式

只有 7 个算子，起步就这些，加算子必须有真实渠道逼出来：

| 算子 | 说明 |
| --- | --- |
| `"$.foo.bar"` | `$ref` 的简写；字符串以 `$.` 开头即视为取值 |
| `{"$literal": x}` | 原样输出，用来输出一个恰好长得像路径的字符串 |
| `{"$coalesce": [a, b, …]}` | 取第一个非空 |
| `{"$if": {"cond": …, "then": …, "else": …}}` | 条件 |
| `{"$map": {"each": …, "as": "item", "do": …}}` | 数组映射 |
| `{"$merge": [a, b, …]}` | 对象浅合并，右侧覆盖左侧 |
| `{"$concat": [a, b, …]}` | 字符串拼接 |

两条相对同类方案的改进：

**① 默认 omitempty。** 求值结果为 null / 空字符串 / 空数组的键**自动不出现在请求里**，需要显式发 null 用 `{"$keep": ...}` 包一层。对照 open-ai-canvas 的 manifest，它 14 个可选字段全部要写 `{"$omitEmpty": {"$ref": ...}}`，噪音占了整份文件的一半。我们写成：

```jsonc
"temperature": "$.temperature",
"max_tokens":  "$.max_tokens"
```

**② 变量是封闭表，不是任意路径。** 宿主注入的根变量只有这些：

| 变量 | 类型 | 说明 |
| --- | --- | --- |
| `$.model` | string | 解析后的模型名（`provider/name` 的后半段） |
| `$.messages` | Message[] | 统一消息，由 `messages` 段翻译 |
| `$.tools` | Tool[] | 工具定义 |
| `$.max_tokens` | int | |
| `$.temperature` | number | |
| `$.stream` | bool | 由宿主按调用路径置位，描述符不该自己写 |
| `$.options.<key>` | any | Agent DSL 里的渠道私有参数透传 |
| `$.cred.<name>` | string | 仅限**非密**凭据字段（如 region）；`type: secret` 的字段**取不到**，只能被 `auth.driver` 使用 |

写错 `$.mesages` 在**加载期**就报错——因为变量表是有限的。这是相对"任意 dot path 字符串"的实质改进。

`$.cred` 对 secret 不可见是硬约束：它杜绝了"某个渠道把 API Key 拼进 body 或 URL"这条泄漏路径，凭据只能经由宿主的鉴权驱动进入请求。

### 3.3 `messages`：厂商差异最集中的地方

同类方案在这里回避了问题——它的宿主内部消息就是 OpenAI 格式，所以 OpenAI 描述符写 `"messages": {"$ref": "request.messages"}` 就完了，而 Anthropic 那种要抽 system、换 tool_result 形状的，就得在描述符里手写一大坨 `$map`。

我们把它变成一个结构化段，由宿主负责铺平：

```jsonc
"messages": {
  "system": "hoist",                    // hoist=抽到顶层字段 | inline=作为首条消息 | prepend_user
  "system_field": "system",             // hoist 时放到请求体的哪个键
  "roles": { "user": "user", "assistant": "assistant", "tool": "tool" },
  "content": "string",                  // string=纯文本 | parts=分块数组

  // content: "parts" 时才需要下面这些
  "text_part":        { "type": "text", "text": "$.text" },
  "tool_call_part":   { "type": "tool_use", "id": "$.id", "name": "$.name", "input": "$.arguments" },
  "tool_result_part": { "type": "tool_result", "tool_use_id": "$.id", "content": "$.content" },

  // 工具调用挂在消息的哪里：inline_parts=混在 content 里（Anthropic）
  //                          sibling_field=同级另一个字段（OpenAI 的 tool_calls）
  "tool_calls": "sibling_field",
  "tool_calls_field": "tool_calls"
}
```

OpenAI 和 Anthropic 的消息差异，从"两段风格迥异的 `$map`"压缩成了十几行配置。

### 3.4 `complete`：非流式

```jsonc
"complete": {
  "method": "POST",
  "path": "/v1/chat/completions",
  "headers": { "OpenAI-Beta": "$.options.beta" },
  "body": {
    "model": "$.model",
    "messages": "$.messages",
    "tools": "$.tools",
    "max_tokens": "$.max_tokens",
    "temperature": "$.temperature"
  },
  "response": {
    "text":      ["choices.0.message.content", "choices.0.text"],   // 依次尝试
    "reasoning": ["choices.0.message.reasoning_content"],
    "tool_calls": {
      "each": "choices.0.message.tool_calls",
      "id": "id", "name": "function.name", "arguments_json": "function.arguments"
    },
    "usage": { "input": "usage.prompt_tokens", "output": "usage.completion_tokens" },
    "error": { "when": "error", "code": "error.code", "message": "error.message" }
  }
}
```

`arguments_json` 而不是 `arguments`：明确声明"这个字段是一段 JSON 字符串，需要解析"。OpenAI 给字符串、Anthropic 给对象，两者用不同的键名区分，而不是靠解释器猜。

### 3.5 ★ `stream`：事件状态机

这是整套设计的核心，也是超出同类方案的地方。

**关键认知：流不是"响应"，是一串改写累加器的事件。** 所以正确的抽象不是路径映射，而是「固定的累加器槽 + 一组事件规则」。

宿主侧的累加器是**固定且有限**的：

| 槽 | 类型 | 说明 |
| --- | --- | --- |
| `text` | strings.Builder | 最终 `CompletionResult.Content` |
| `reasoning` | strings.Builder | 思维链（若渠道提供） |
| `blocks[idx]` | 索引化槽位 | `{kind, id, name, args strings.Builder}` |
| `usage.in / usage.out` | int64 | |
| `err` | error | 一旦置位，整轮以失败结束 |

规则可用的操作也是封闭集：`emit_text` / `emit_reasoning` / `open` / `close` / `set_id` / `set_name` / `append_args` / `usage_in` / `usage_out` / `fail`。**没有循环、没有赋值、没有用户自定义变量**——可枚举、可测、可 fuzz。

#### OpenAI 式（无事件名，靠数据判别）

```jsonc
"stream": {
  "request": { "patch": { "stream": true, "stream_options": { "include_usage": true } } },
  "transport": "sse",
  "done": ["[DONE]"],
  "on": [
    { "emit_text":      "$.choices.0.delta.content" },
    { "emit_reasoning": "$.choices.0.delta.reasoning_content" },
    { "each": "$.choices.0.delta.tool_calls", "index": "$.index",
      "set_id": "$.id", "set_name": "$.function.name", "append_args": "$.function.arguments" },
    { "usage_in": "$.usage.prompt_tokens", "usage_out": "$.usage.completion_tokens" },
    { "fail": "$.error.message" }
  ]
}
```

`request.patch` 与 `complete.body` 浅合并——流式和非流式共享同一个请求模板，只声明差异。这条约束顺带保证了两条路径不会漂移。

#### Anthropic 式（事件类型分派 + 增量 JSON）

```jsonc
"stream": {
  "request": { "patch": { "stream": true } },
  "transport": "sse",
  "event_type": "$event",                     // 取 SSE 的 event: 行
  "on": [
    { "match": "message_start",       "usage_in": "$.message.usage.input_tokens" },
    { "match": "content_block_start", "open": { "index": "$.index", "kind": "$.content_block.type",
                                                "set_id": "$.content_block.id",
                                                "set_name": "$.content_block.name" } },
    { "match": "content_block_delta", "index": "$.index", "switch": "$.delta.type", "cases": {
        "text_delta":       { "emit_text": "$.delta.text" },
        "thinking_delta":   { "emit_reasoning": "$.delta.thinking" },
        "input_json_delta": { "append_args": "$.delta.partial_json" }
    } },
    { "match": "content_block_stop",  "close": "$.index" },
    { "match": "message_delta",       "usage_out": "$.usage.output_tokens" },
    { "match": "error",               "fail": "$.error.message" }
  ]
}
```

**七条规则，等价于现在 `gateway.go` 里那 130 行手写累加。**

#### 必须写死的语义（否则渠道作者会各写各的）

- `emit_text` 同时做两件事：调 `onDelta(StreamDelta{TextDelta: …})` **并且**追加到 `text` 槽。作者不会漏掉其中一件。
- `append_args` 只累加、**不 emit**——半截 JSON 推给前端没有意义，也无法执行。
- `close` 时才 `json.Unmarshal(args)`。**解析失败 = 整轮失败**，不静默丢弃：丢一个工具调用会让 agent 卡在"我以为我调了"的状态，比直接报错难查十倍。
- 没有 `open`/`close` 的渠道（OpenAI）：槽位按 `index` 隐式创建，流正常结束时隐式全部 close。
- 规则**按声明顺序全部尝试**，不是首个命中即停——一个 SSE 事件里可能同时带 delta 和 usage。`match`/`switch` 不命中则跳过该条。
- `transport` 支持 `sse` / `ndjson` / `json-array`；解析框架由宿主实现，描述符不碰分帧。

### 3.6 `auth`：封闭驱动集

描述符只能**点名**驱动并指定用哪个凭据字段，绝不能实现算法：

```jsonc
"auth": { "driver": "bearer", "credential": "api_key", "header": "Authorization", "prefix": "Bearer " }
```

宿主实现的驱动：`none` / `bearer` / `header` / `query` / `basic` / `anthropic` / `google-api-key` / `aws-sigv4` / `volcengine-v4` / `tc3`。签名类（sigv4/v4/tc3）需要读 body 做摘要，本质上不可声明式表达，**这是设计上的有意封口，不是暂时的偷懒**。

新增一种签名 = 改 Go = 发版本。这是可接受的：签名协议的新增频率远低于新增渠道。

## 四、可靠性设计（声明式的对症药）

同类方案缺的就是这一块，而这恰恰决定了这套体系是"降本"还是"换个地方受苦"。

### 4.1 加载期校验（装的时候就报错）

- 表达式里的根变量在白名单内；路径语法合法。
- `capabilities` 与实际存在的段一致。
- `auth.driver` 在宿主驱动表内；`auth.credential` 指向 `credentials[]` 里真实存在的字段。
- 状态机规则里的 `index` 只在有索引槽的操作上出现；`switch` 必须带 `cases`。
- `$.cred.<x>` 不指向 `type: secret` 的字段。

装插件时一次性抛出**全部**错误（不是遇到第一个就停），附字段路径。

### 4.2 fixtures：每个渠道自带回归测试

描述符包里必须带 `fixtures/`：

```jsonc
// fixtures/tools.json
{
  "request": { "model": "gpt-4o", "messages": [...], "tools": [...] },
  "expect_http": { "method": "POST", "path": "/v1/chat/completions", "body": { ... } },
  "complete_response": "<上游真实响应 JSON>",
  "stream_response": "<上游真实 SSE 原始字节>",
  "expect_result": { "content": "...", "tool_calls": [...], "input_tokens": 12, "output_tokens": 34 }
}
```

- **安装期跑一遍，过不了不给装。**
- ★ **同一份 `expect_result` 同时校验 `complete_response` 和 `stream_response`。** 这条是整套设计里性价比最高的一条：它强制"流式和非流式产出同构结果"，把声明式最容易出的那类 bug（流式漏了 usage、tool_call 的 id 没接上、reasoning 只在一条路径上有）在装机时就挡掉。

### 4.3 `explain`：不用抓包

`GET /model-channels/{id}/explain?fixture=basic` 返回渲染后的完整 HTTP 请求（凭据脱敏成 `***`）。调渠道时能直接看到"我这份描述符最终发出去的是什么"。

### 4.4 运行时 trace

按 run 记录每条状态机规则的命中次数。上游改了字段名时，一眼能看出是"规则没命中"还是"命中了但值是空"——这是声明式最难查的一类故障。

## 五、必须一并修掉的既有问题：流式 + 降级链

`Gateway.CompleteStream` 现在走 `resolve` 的降级链。**如果第一环已经通过 `onDelta` 吐出了半段文字才失败，切到第二环重新生成，前端会拼出两段内容。**

这个 bug 现在就存在（`gateway.go:251`），只是流式渠道少、没撞上。做描述符时必须定掉：

> **CompleteStream 的降级只在尚未 emit 任何 delta 时允许；一旦 emit 过，失败就直接抛出，不再降级。**

实现上给 `resolve` 传一个 `canFallback func() bool`，流式路径下它读一个"是否已 emit"的标志位。非流式路径行为完全不变。

代价是：一个在中途断流的渠道不会被兜住，用户会看到一个失败的运行。这是对的——**半截答案比一个明确的失败更糟**，后者至少可以重试。

## 七、分阶段落地

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| P0 | 描述符 schema + 表达式 + 请求渲染 + 非流式响应映射 + 加载期校验 | `openai.chat.v1` 一份描述符跑通 deepseek / qwen / custom 三个渠道，`registry.go` 里删掉对应的 `openAICompatibleFamily` 项 |
| P1 | ★ 流式状态机 + SSE/NDJSON transport + `messages` 段 | OpenAI、Anthropic 两份描述符流式跑通；`gateway.go` 的手写 anthropic 流式作为对照保留，二者对同一 fixture 产出一致 |
| P2 | fixtures 安装期自检 + complete/stream 一致性断言 + `explain` 接口 | 故意写错一个路径，装不上去且报错能定位到字段 |
| P3 | 接入 spec-20 插件（`extensions.model_providers[]`）+ Credential 泛化 + 前端动态表单 | 从组件广场装一个第三方渠道并成功跑一次对话 |
| P4 | 降级链修复（第五节）+ embed + probe | 流式中途失败不再拼接两段内容 |
| P5（可选） | 异步任务型渠道（图片/视频）：`task` 段 create→poll→cancel→result | — |

P0+P1 是最小可用集，也是这套体系立不立得住的判据：**如果 Anthropic 的流用七条规则表达不出来，就该退回混合模式，只让描述符覆盖 OpenAI 兼容那一大类。**

## 八、风险与取舍

| 风险 | 缓解 |
| --- | --- |
| 表达式/状态机是个自研小语言，要写文档、要维护 | 算子和操作都是封闭集，加任何一个都要有真实渠道逼出来；配 `explain` + trace 降低调试成本 |
| 某个厂商的流协议表达不出来 | 混合模式：退回手写 Go client，两者在同一注册表里平权。这是**设计内的出口**，不是失败 |
| 描述符写错导致线上渠道不可用 | fixtures 安装期自检 + 加载期校验；描述符走 spec-20 的审核流程 |
| 前期投入 ≈ 2000 行 Go | 只有在打算铺几十个渠道（尤其国内 OpenAI 兼容中转）时才划算。若一年只加两三个渠道，**不要做这套**，继续手写 client 更省 |

最后一条是诚实的：**这套体系的收益随渠道数量线性增长，成本是一次性的。** 决定做之前先确认渠道数量的预期。

## 九、与 open-ai-canvas（`yingce.plugin/v2`）的对照

| 维度 | open-ai-canvas | 本设计 |
| --- | --- | --- |
| 流式 | ✗ 不支持，归一成最终响应 | ★ 事件状态机，一等公民 |
| 表达式算子 | 25+ | 7，加算子需真实渠道逼出 |
| 可选字段 | 每个都要 `{"$omitEmpty": …}` | 默认 omitempty |
| 变量寻址 | 任意 dot-path 字符串 | 封闭变量表，写错在加载期报错 |
| 凭据可见性 | 未见约束 | secret 字段对表达式不可见 |
| 消息翻译 | 各渠道自己写 `$map` | 结构化 `messages` 段 |
| 回归保障 | 无 | fixtures 安装期自检 + 流/非流一致性 |
| 调试 | 生成的 interface.md | `explain` 接口 + 运行时规则命中 trace |
| 异步任务 | ✓ create/poll/cancel/result | P5 预留 |
| 分发 | 独立插件包体系 | 复用 spec-20 插件（安装/版本/审核/市场全部白捡） |

值得抄的两点，本设计已吸收：**Adapter 只做协议翻译、宿主保留凭据与出网**（这条边界划得非常正确），以及**鉴权驱动是宿主实现的封闭集**。
